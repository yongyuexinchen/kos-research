# KOS 项目整改与指导建议书

> 文档编号：R1
> 日期：2026-08-19
> 范围：KOS（个人认知演化系统）架构评审五报告之一——项目整改与指导建议
> 定位：针对架构评审发现的核心问题给出可执行整改动作；衔接培训期低功耗维护与 12 月后工程化（FastAPI + PostgreSQL + pgvector）
> 优先级：P1=冲刺期（黑马低功耗模式）内可执行的低成本动作；P2=12 月后恢复全量维护时执行；P3=工程化阶段落地
---

## 一、总述

KOS 当前处于阶段 1 到 2 的过渡期，MVP 以 Hermes + Obsidian 维护，未来工程化为 FastAPI + PostgreSQL + pgvector 项目。评审发现九个核心问题，分三类：

- 流程断裂类（问题 1-5）：数据流铁律与反馈机制存在缺口或断层，信号在层间传递时丢失或失真；
- 机制空转类（问题 6）：顶层设计未转化为可触发的日常操作；
- 系统自噬类（问题 7-9）：维护成本、验收摩擦与复苏风险威胁系统可持续性。

整改总原则：不新增 OS 模块，所有改进映射到现有层与现有文件；培训期只执行 P1，P2 推迟到恢复全量维护后，P3 作工程化设计预留。

---

## 二、问题清单与整改动作

### 问题 1：D11 数据型与判断型反馈未区分，辩论门槛一刀切

**现象**：D11 铁律规定行动结果进入知识层/认知层均须经提问辩论。实际执行中，投资成交记录、定投扣款流水、实验播放量等纯数据回填与"某板块逻辑失效"等判断更新走同一门槛：数据被辩论环节阻塞，要么延迟入库要么绕道别处；判断反而可能因流程疲劳被放行。

**根本原因**：D11 把"双导出需辩论"写成无差别约束，源头未区分反馈性质。辩论是认知加工手段，不是数据登记手段；数据回填只需源头可溯，判断更新才需攻防验证。

**改进动作**：
- P1：拆分 D11 为两个子通道。D11a 数据回填（事实/事件/指标），无需辩论，仅要求 `sourced_from` 指向行动记录；D11b 判断导出（结论/认知更新），维持辩论。卡 frontmatter 增加 `feedback_type: data|judgment` 字段，落库时先分类再选通道。
- P2：判断通道辩论分级：与既有判断一致、仅补证据的，简化为一轮自问自答；推翻既有判断或影响体系卡 status 的，走完整 F6 对辩。
- P3：工程化后 `feedback_type` 映射为表字段，数据回填走批量接口，判断更新走审批流。

### 问题 2：位置改变操作与 Current.md 更新之间缺乏连接机制

**现象**：Current.md 定位为运行时位置快照（身份/主目标/约束/风险），但位置改变并不必然触发更新。08-12 进入冲刺模式、08-15 拍板不考、08-16 切换黑马模式——关键位置变更靠手工记忆补写，位置校准协议未落成机制。

**根本原因**：位置哲学定义了 Current.md 的工程接口，但未定义"位置改变"的操作型判据与触发条件，未与决策、苗床记录挂钩。

**改进动作**：
- P1：定义位置变更判据：任何决策级变更（有决策记录落库）或阶段切换必须同步更新 Current.md，写入 F1 流程；决策记录 frontmatter 增加 `updates_current: yes|no` 字段，Hermes 落决策时校验，缺失视为流程未完成。
- P1：Current.md 增加位置变更日志区（version / 变更时间 / 变更原因引用决策 ID），旧内容不删（历史由 git 保留）。
- P2：周五巡检（F5）增加"位置核对"步骤：对比本周决策记录与 Current.md，不同步则补更。
- P3：工程化后建 `state_snapshots` 表（snapshot_id / valid_from / valid_to / position_json），Current.md 退化为其物化视图。

### 问题 3：时效性强场景无快速响应通道，信号绕过延迟路径

**现象**：投资信号（体系卡 S1-S5 月度核对）走标准延迟路径（观察→模型→行动→反馈），而市场信号时效以天甚至小时计。月度节奏与信号时效不匹配，实际执行中要么错过窗口要么绕开系统直接行动。F7 待设计区"信号监测频率"长期未定稿。

**根本原因**：所有路径按批处理节奏设计（月度核对、周五巡检），未区分高时效信号与低时效知识，信号监测频率长期未定稿。

**改进动作**：
- P1：建立快通道：定义高时效场景清单（投资信号、健康复查提醒、决策截止日），清单内场景允许"先行动记录、后补沉淀"——当天在 Position 布局卡记一行事实，分析顺延至最近一次巡检。
- P1：体系卡 frontmatter 增加 `signal_frequency: daily|weekly|monthly` 字段，投资类标 daily，触发巡检外快速核对；最低要求做到"信号当天记一行，周五巡检补全分析"。
- P2：S1-S5 月度核对细化为"日历核对 + 事件驱动核对"双轨，事件判据写入体系卡 trigger 字段（如"指数单日波动超阈值或个股跌破止损线"）。
- P3：工程化后建 `signals` 表（signal_id / card_id / observed_at / severity / responded_at），pgvector 关联体系卡，cron 生成每日核对清单。

### 问题 4：苗床层 T1 只覆盖 Hermes 会话，非会话场景苗头丢失

**现象**：苗床层三触发器 T1 对话 / T2 巡检 / T3 决策前中，T1 依赖 Hermes 会话出现未固化表达。独处念头、阅读时的判断动摇、手机备忘录里的情绪信号均不经会话，苗头全部丢失；T2 回看"本周对话"也只覆盖会话记录。

**根本原因**：苗头捕捉通道绑定在单一入口（Hermes 对话），未枚举苗头产生的全场景；"捕捉成本 30 秒内"与现状不匹配。

**改进动作**：
- P1：苗床入口扩展为四通道：① Hermes 对话（T1 保持）；② 手机备忘录自记（建 `Radar/Seedbed/inbox.md` 暂存，巡检归位）；③ 阅读划线旁注（Obsidian 高亮视为潜在苗头，巡检扫描）；④ 决策前扫苗床（T3 保持）。
- P1：固化最短记录格式（`[类型] 苗头（情境）→ 处置`，30 秒内），培训期配额"每周至多 3 条"，防苗床成新负担。
- P2：T2 增加"非会话场景扫描"：扫本周高亮段落与 inbox 未归档条目。
- P3：工程化后建 `seedbed_entries` 表（entry_id / category / source_channel / captured_at / status: fresh|escalated|expired），按通道统计捕捉率调优。

### 问题 5：BDA 目标系统评估未标准化（级联盲区）

**现象**：BDA 模板 v1.1 四要素中，物理毁伤评估（Reality 回填）与功能毁伤评估（Gap 分析）已就绪；目标系统评估明确标注"缺口：未标准化"；再攻击建议仅 Experiment Card 有 next_action，普通行动无。实际执行只回答"这一仗打没打赢"，不回答"对整条战线的影响"。

**根本原因**：BDA 模板按单行动设计，缺少"目标系统"定义（哪些卡属该系统、连锁影响如何查）；军事映射第三设计约束标注"12 月后施工"，模板已升 v1.1 却未补齐该节。

**改进动作**：
- P1：bda.md 模板 E 节补标准化结构，固定三字段：① 相关体系卡清单（受影响 Systems 卡 ID）；② 连锁影响判断（无影响 / 局部 / 级联，含对 KOS 三指标影响）；③ 级联触发判据（哪些卡的状态机需复查，可空）。至少填前两项。
- P1：BDA 流程增加"系统级复查"：评估后检查受影响体系卡状态机是否需推进（对照 F4"无判据不推进"），并在体系卡更新日志引用 BDA ID。
- P2：再攻击建议推广至所有行动：bda.md J 节改必填，普通行动至少写"维持 / 调整 / 终止"三选一加一句理由。
- P3：工程化后建 `bda_assessments` 表（assessment_id / action_id / physical / functional / system / reattack），system 存 JSON（related_cards / cascade_flag / notes）。

### 问题 6：七条哲学编译链实际运行率约 30-40%

**现象**：七条编译链（本体/推理/演化/行动/自我/研究协议/分析操作符）设计完整且全部映射到现有层，但实际运行率仅约 30-40%。大部分链只存在于架构文档：分析操作符（EGS 八问）依赖 Hermes 自觉，推理工程（情报处理层）仅在调研报告中偶发出现。

**根本原因**：编译链以"设计原理"形态停留在架构文档，未定义触发条件、最小执行动作与验收标准；"编译不等于硬编码"被误读为"不落地"，实际应理解为"落成可调用协议而非自动决策引擎"。链的运行依赖 Hermes 对文档的记忆，无入口清单。

**改进动作**：
- P1：为每条链建单页操作卡，置于 `Maintain/layers/all/compilation-chains/`，每卡三要素：触发条件、最小执行动作（3-5 步，30 分钟内）、验收标准（产物）。七卡对应七条链。
- P1：先选两条链跑通闭环并沉淀模板：行动工程链（链 4，配投资决策案例）与分析操作符链（链 7，配社会新闻走 EGS 八问案例），其余 P2 跟进。
- P2：链的执行痕迹纳入周五巡检：统计各链本周触发次数，低于阈值的下月补一次演练。
- P3：工程化后链定义转化为 pipeline 定义文件，触发条件翻译为可校验 schema。

### 问题 7：系统自增长风险——文档与架构消耗大量维护时间

**现象**：设计文档体系庞大（架构收敛版、卡片类型体系、设计思考、实际设计快照、编译链、各层技能），架构调整要求"三件套同步"（架构文档 + BOOTSTRAP + 维护技能），同步成本随文档数量增长。用户已在 Current.md 风险区记录"知识库建设投入大于求职备考投入（自证循环风险）"与"容易陷入系统建设循环"。

**根本原因**：系统把"设计文档完整性"当成目标，文档同步成本近似平方增长；"不横向扩展"红线只约束 OS 模块，未约束文档本身；维护预算与文档维护量矛盾被低估。

**改进动作**：
- P1：确立文档冻结线：架构收敛版 v2.0 冻结为只读基准，除修错外不再新增章节；新设计想法只进设计思考待定区，拍板后只落一个位置。
- P1：废止"三件套同步"为"单点落盘"：决策只更新一个权威文件，BOOTSTRAP 与技能改为引用链接，消灭同步成本。
- P1：培训期维护预算硬上限：每周 3-5 小时中系统维护占比不超过一半；Current.md 增加"系统维护时长"周记录字段，超预算下周纯只读。
- P2：每季度一次架构垃圾回收：归档已落地条目的快照与过时文档，Maintain 文档总量控制在约 30 个文件内。

### 问题 8：12 项建卡验收标准执行摩擦偏高

**现象**：建卡必循模板 12 项验收（另有验收 9 项表述），叠加四段式、双链不少于 3、frontmatter 校验等要求，单卡验收流程重。培训期"只读不建"下验收标准闲置，恢复建卡后摩擦将立刻显现；Agent 拆卡历史返工率已证明逐项人工核对成本高。

**根本原因**：验收是清单式逐项人工核对，未区分"机器可校验项"与"人工判断项"，也未按卡型分级，事实卡与判断卡承受相同验收强度。

**改进动作**：
- P1：12 项拆两层：机器层（frontmatter 字段完整、命名日期格式、双链数量、目录归属、格式一致性）由脚本自动校验，扩展 check_cao_format.py 覆盖可自动化部分；人工层（内容非空、论证链质量、连接真实性）保留 3-4 项，人工核对清单降至不超过 4 项。
- P1：按卡型分级验收：事实型卡（Concept、Observation）走机器层加快速抽查；判断型卡（Judgment、体系卡、认识卡）走完整验收加辩论。口径改为"机器 8 项一律执行 + 人工 4 项按卡型分级"。
- P2：验收清单固化进 book-card-extraction 与 kos-cao-pipeline 的验收环节，staging 目录放 acceptance-checklist.md 模板，勾选留痕。
- P3：工程化后验收翻译为数据库约束：CHECK 管 frontmatter 必填，触发器管双链完整性，12 项自动化为 12 条约束，摩擦归零。

### 问题 9：系统长期低维护后缺乏明确复苏成本评估

**现象**：黑马低功耗模式持续约四个月，期间技能生疏、流程断点、模板变更未同步、文档与库脱节将累积。系统没有任何机制评估恢复全量维护的成本，复苏时可能发现恢复成本高于预期，或直接放弃。

**根本原因**：系统设计从未把"低维护期"当作一等场景，所有流程假设持续运行；未定义保底资产清单（哪些必须保持最新、哪些允许腐烂），也没有复苏预算估算方法。

**改进动作**：
- P1：定义保底资产清单（培训期只保三样）：① Current.md 位置快照；② 苗床月度文件（记录即可，不加工）；③ 周五巡检状态机核对。其余（模板演进、编译链演练、文档同步）明确允许腐烂，写入 Current.md 低功耗模式节。
- P1：建立复苏清单，置于 Maintain/BOOTSTRAP.md：① 读 Current.md 与架构收敛版（30 分钟）；② 跑 F1-F5 自检（查各层 index 失效链接）；③ 苗床过期条目清理与升格；④ 验收脚本统计格式漂移；⑤ 试建一张概念卡验证管道。复苏总预算 4-6 小时，写进清单使复苏可预期。
- P2：低维护期结束前两周设"复苏预演"：只跑复苏清单第 5 步，提前发现管道断裂。
- P3：工程化后复苏清单固化为脚本（check_links.py / validate_cards.py），一键输出复苏状态报告。

## 三、施工禁区（冲刺期间绝对不能动）

以下内容在培训期乃至恢复全量维护前期一律禁止改动，改动前必须先立项并经用户拍板。

1. **五层架构与 D1-D12 数据流铁律**：架构收敛版 v2.0 冻结为只读基准，分层结构、数据流方向、禁止直达约束（D3/D4/D7）不改。本建议书的通道拆分（问题 1、3）是现有铁律内的细化，不是重写。
2. **顶层设计定稿**：EGS 公理、位置哲学、军事映射均为用户定稿，不施工不修改，任何整改不得与之冲突。
3. **收敛规范 v2.0**：四型目录、四段式、双链不少于 3，拆卡唯一规范，冻结不改。
4. **拆卡与吸收流水线纪律**：F3/F3.5 的预算纪律（30 次上限）、"模型只产出不落地"、"子代理自报不可信——验收看文件"三条铁律不动。
5. **知识层存量数据**：不迁移旧库，不批量重命名，平铺节点与 CAO 卡保留。
6. **辩论与分层纪律**：F6"用户说停才停"铁律不动；苗床双层信号分层纪律（个人侧产出不直接动体系卡 status）不动。问题 1 的辩论分级只调整强度，不取消辩论。
7. **培训期维护预算**：每周 3-5 小时上限与保底清单是硬约束，任何 P1 动作不得突破；P2/P3 不提前施工。
8. **不横向扩展红线**：所有改进映射到现有层与现有文件；P3 表结构只作设计预留，Obsidian 阶段不建任何新目录。
9. **历史记录**：Current.md 旧版本、演化史、苗床归档不删不改，历史由 git 版本控制保证。

## 四、整改节奏

- 冲刺期（黑马低功耗模式，即日起至 12 月）：执行 P1 轻量项——feedback_type 字段、位置变更日志区、快通道清单、苗床 inbox 通道、BDA 模板 E 节三字段、文档冻结线与单点落盘、维护时长记录、验收机器层脚本扩展、保底资产清单与复苏清单。新增维护量控制在每周 1-2 小时内。
- 恢复期（12 月后）：执行全部 P2，按复苏清单顺序推进，先验证管道再升级流程。
- 工程化阶段：执行全部 P3，本建议书标注的表结构与字段即为数据库 schema 设计输入。

---

## 五、结语

KOS 的核心价值是保存"我如何从不知道到知道再到发现自己错了"，而非保存文档本身。九个问题的整改共同指向一个原则：**让机制接住信号，让用户只做判断**。数据回填自动化、位置同步巡检化、高时效信号快通道化、验收机器化，是把维护时间从系统自噬中释放，还给学习、作品与生活。培训期的意义不在维护系统，而在用系统维护自己。
